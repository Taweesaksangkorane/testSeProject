## Feedback จากอาจารย์ (สรุปจากบทถอดเสียงการประชุม)

### 1. กลับไปยึดฟังก์ชันหลักและโจทย์ของระบบ

- จุดมุ่งหมายหลักไม่ใช่เพียงแปลงเอกสารเป็น PDF หรือสกัดข้อมูล แต่ต้องช่วยให้ **นักวิจัยติดตามสถานะโครงการ** และให้เจ้าหน้าที่บริหารจัดการข้อมูลและการดำเนินงานได้จริง
- อาจารย์ขอให้ทบทวนว่า หลังนักวิจัยกรอกข้อมูลและส่งข้อเสนอแล้ว เจ้าหน้าที่จะตรวจ **ข้อมูลอะไร จากแหล่งไหน และดำเนินการอย่างไรต่อ**

### 2. Data Extraction และการแสดงผลข้อมูลจริง

- เอกสาร RS-1 จริงมีรูปแบบแตกต่างกัน จึงต้องอธิบายข้อจำกัดการสกัดข้อมูลและแนวทางให้นักวิจัยตรวจสอบ/แก้ไขข้อมูลที่นำเข้า
- การใช้ข้อมูลตัวอย่างสั้น ๆ ใน Prototype ยังไม่สะท้อนข้อมูลจริง เช่น ความสำคัญของปัญหา การทบทวนวรรณกรรม หรือระเบียบวิธีวิจัยที่อาจมีข้อความยาวมาก
- ต้องออกแบบหน้าอ่านและตรวจข้อเสนอให้รองรับข้อความหลายย่อหน้า พร้อมระบุข้อมูลและจุดตรวจสอบที่ชัดเจน ไม่ใช่มีเพียงปุ่ม “ตรวจผ่าน”
- อาจารย์ให้ปรับ **ฟอนต์ของหน้าจอ** ให้เหมาะสม

### 3. User Flow สำหรับเจ้าหน้าที่และการเปลี่ยนสถานะ

- ต้องระบุให้ชัดว่า **ใครเป็นคนอัปโหลดเอกสาร อัปโหลดเมื่อใด เจ้าหน้าที่ตรวจอะไร และผลตรวจทำให้เกิดขั้นตอนใด**
- ต้องกำหนดสถานะโครงการและเงื่อนไขเปลี่ยนสถานะ ไม่ปล่อยให้การกดปุ่มใน Prototype เป็นเพียงการจำลองโดยไม่มีข้อกำหนด
- ต้องออกแบบกรณีส่งกลับแก้ไข รวมทั้งหลักฐานหรือข้อมูลที่ใช้ประกอบการตรวจและรับรอง
- หน้า “ตรวจปิดโครงการ” ควรแสดงรายการโครงการที่อยู่ระหว่างรอตรวจปิด ไม่ใช่พาผู้ใช้วนไปยังรายการโครงการทั้งหมดโดยไม่สอดคล้องกับงานที่ทำ
- ต้องมี Flow ที่นักวิจัยส่งเอกสารปิดโครงการจริงก่อนเจ้าหน้าที่เข้าตรวจ ไม่ควรแสดงว่าโครงการพร้อมปิดโดยไม่มีแหล่งที่มาของเอกสาร

### 4. User Flow สำหรับผู้ทรงคุณวุฒิ

- การประเมินต้องออกแบบจากมุมมองของผู้ทรงคุณวุฒิจริง ไม่ใช่เพียงย้ายแบบฟอร์มกระดาษมาเป็นหลายหน้าที่ต้องกดไปมา
- ผู้ทรงควร **อ่านเนื้อหารายงานที่สัมพันธ์กับหัวข้อประเมินได้พร้อมกับกรอกแบบประเมิน** เช่น เปิดวัตถุประสงค์ของงานวิจัยควบคู่กับคำถามว่าบรรลุวัตถุประสงค์หรือไม่
- พิจารณารูปแบบหน้าจอที่ลดการสลับหน้าระหว่างเอกสาร รายละเอียดโครงการ และแบบประเมิน เช่น แสดงข้อมูลและแบบประเมินเคียงกันหรือเลื่อนในหน้าเดียว
- ต้องทดลองใช้งานตามเรื่องราวของผู้ใช้จริง อ่านข้อมูลและตอบแบบประเมินจริง ไม่ใช่ทดสอบเพียงว่าปุ่มกดได้

### 5. Requirement Specification และการจัดการงานใน GitHub

- อาจารย์ระบุว่าเอกสาร Requirement ยังไม่ครบและไม่ละเอียดพอ เช่น ขาดเงื่อนไขการยื่นเอกสาร การตรวจสอบ สถานะ การส่งกลับแก้ไข และการปิดโครงการ
- ต้องจัดทำ/ปรับปรุง **Requirement Statements, Acceptance Criteria, User Flow, Use Case Diagram และรายละเอียดของแต่ละ Flow** ให้ตรวจสอบย้อนกลับได้
- ต้องเก็บ Requirement และเอกสารออกแบบใน GitHub เป็น **Baseline** กลางของทีม พร้อมอัปเดตเมื่อมีการเปลี่ยนแปลง ไม่ควรอ้างอิงเฉพาะ Proposal หรือปรับ Prototype ตามคำถามในการประชุมไปเรื่อย ๆ
- ต้องทำให้ **Requirement, Prototype, เอกสารส่ง Final และงานใน GitHub** สอดคล้องกัน และบันทึกว่าแต่ละฟีเจอร์ทำถึงไหน ใครรับผิดชอบ และตรวจจากข้อกำหนดใด
