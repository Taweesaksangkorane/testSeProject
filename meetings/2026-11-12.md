## ผลการวิเคราะห์และแนวทางปรับปรุง Prototype

จากการจัดทำเอกสาร ทีมได้กำหนดแนวทางสำหรับปรับปรุง Prototype ดังนี้

1. **การจัดทำและยื่นข้อเสนอโครงการ:** รองรับการกรอกข้อมูล RS-1 และแนวทางอัปโหลดเอกสารเพื่อสกัดข้อมูล โดยให้นักวิจัยตรวจสอบข้อมูลก่อนบันทึก
2. **กระบวนการตรวจสอบข้อเสนอ:** แยกการพิจารณาของต้นสังกัดซึ่งดำเนินการภายนอก Web ออกจากการตรวจเอกสารของเจ้าหน้าที่ภายในระบบ
3. **การติดตามสถานะ:** กำหนดสถานะโครงการหลัก 8 สถานะ พร้อมเงื่อนไขการเปลี่ยนสถานะและการส่งกลับแก้ไข
4. **บทบาทและสิทธิ์ผู้ใช้:** กำหนดบทบาทในระบบเป้าหมาย ได้แก่ นักวิจัย เจ้าหน้าที่ส่วนบริหารงานวิจัย และผู้ทรงคุณวุฒิ
5. **การดำเนินงานและปิดโครงการ:** แยกการขยายเวลาผ่าน e-Office และการปิดโครงการออกเป็นสองเส้นทาง ได้แก่ รายงานวิจัย 5 บท และผลงานเผยแพร่

แนวทางดังกล่าวยังอยู่ในขั้นตอนการวิเคราะห์และออกแบบ โดยจะนำข้อเสนอแนะจากอาจารย์และ Stakeholder ไปใช้กำหนดขอบเขตของ Prototype ที่จะพัฒนาจริง

## ประเด็นที่นำเสนอและขอการยืนยัน

1. ขอบเขตฟังก์ชันที่จำเป็นสำหรับ Seminar Prototype เทียบกับ Requirements v1.5
2. ความถูกต้องของ Workflow, User Flow และ Use Case เมื่อเปรียบเทียบกับขั้นตอนปฏิบัติงานจริง
3. บทบาทผู้ใช้ สิทธิ์การเข้าถึง และผู้รับผิดชอบในแต่ละขั้นตอน
4. ความเหมาะสมของสถานะโครงการทั้ง 8 สถานะ รวมถึงเงื่อนไขการเปลี่ยนสถานะและการส่งกลับแก้ไข
5. Acceptance Criteria และ Open Questions ที่ยังต้องได้รับการยืนยันก่อนนำไปพัฒนา

## Feedback จากอาจารย์ (สรุปจากบทถอดเสียงการประชุม)

### 1. Project Ownership และการบริหารโครงการ

- ทีมต้องเป็นเจ้าของโครงการ เข้าใจ Scope, Deliverables, Timeline และติดตามความคืบหน้าด้วยตนเอง ไม่รอแก้เฉพาะสิ่งที่อาจารย์แจ้งรายสัปดาห์
- ต้องแยกงานพัฒนาระบบออกจากงานเอกสารส่งรายวิชา และตรวจสอบว่า Seminar ต้องส่งอะไรบ้าง
- ควรนำเสนอความคืบหน้าเทียบแผน รวมถึงงานที่ล่าช้าและสิ่งที่จะดำเนินการต่อ

### 2. Final Seminar Paper

- จัดทำ Paper ภาษาอังกฤษตาม IEEE Template ความยาวไม่เกิน 6 หน้า พร้อม References
- อธิบายเหตุผลและปัญหาที่นำไปสู่การพัฒนาระบบ Requirements ที่ได้รับ และแนวทางออกแบบและพัฒนาระบบ
- ศึกษาตัวอย่างที่อาจารย์ให้ไว้ และตรวจสอบรายละเอียดการส่งใน Google Classroom อีกครั้ง
- วันสุดท้ายของการส่ง Final Document คือวันพุธที่ 18 พฤศจิกายน 2026

### 3. Transition to Senior Project 1 และ Senior Project 2

- จัดทำแผนขอบเขตงานทั้งหมด ระบุผลงานที่เสร็จใน Seminar และสิ่งที่จะพัฒนาต่อใน SP1/SP2
- ขยายรายละเอียด Methodology (บทที่ 3 ของเอกสารโครงการฉบับเต็ม), Architecture Style, System Design และ Technology Stack พร้อมเหตุผลในการเลือก
- วางแผนการพัฒนา การทดสอบกับผู้ใช้จริง การปรับปรุงระบบ Timeline, Deliverables และผู้รับผิดชอบ โดยไม่ถือว่าตัวอย่างระยะเวลาที่อาจารย์ยกขึ้นมาเป็นแผนที่อนุมัติแล้ว

### 4. GitHub Repository Management

- ใช้ Private Repository เป็นพื้นที่กลางที่สมาชิกและอาจารย์เข้าถึงได้ เก็บ Source Code ของ Prototype เอกสารฉบับล่าสุด และแผนงาน
- ให้สมาชิก Commit งานของตนอย่างต่อเนื่อง พร้อมระบุสิ่งที่แก้ไขและผลกระทบ ไม่รอนำงานทั้งหมดขึ้นในช่วงท้าย
- ส่งลิงก์ Repository ให้อาจารย์ผ่านกลุ่มแชทอีกครั้ง

### 5. Requirement Change Management และ RS-1 Document Extraction

- เมื่อมี Requirement หรือเอกสารใหม่ ให้บันทึกวันที่ได้รับ วิเคราะห์ผลกระทบต่อข้อกำหนดและความสามารถของระบบ ทบทวนเอกสารที่เกี่ยวข้อง แล้ว Commit การเปลี่ยนแปลงลง GitHub
- อาจารย์อนุญาตให้นำแนวทางการสกัดข้อมูลตัวอย่างมาศึกษาและปรับปรุงต่อ โดยเน้นเข้าใจมุมมองนักวิจัยและลดภาระการกรอกข้อมูล ไม่ใช่เพียงรับ Input และบันทึกฐานข้อมูล

### 6. Final Presentation

- นำเสนอปัญหา Requirements แนวทางแก้ไข System Design วิธีพัฒนา Technology Stack พร้อมเหตุผล ความคืบหน้า แผน SP1/SP2 สิ่งส่งมอบ ระยะเวลา และการแบ่งงาน
- อธิบายด้วยความเข้าใจและใช้แผนภาพประกอบตามความเหมาะสม อาจารย์ไม่ได้กำหนดลำดับหัวข้อแบบตายตัว
- นำเสนอในสัปดาห์สุดท้ายของรายวิชา โดยรูปแบบ On-site ยังรอการยืนยัน

> ข้อเสนอแนะข้างต้นมาจากอาจารย์ ไม่ใช่คำยืนยัน Requirements รายข้อจาก Stakeholder

## สรุปการประชุม

อาจารย์เน้นให้ทีมรับผิดชอบโครงการในฐานะเจ้าของงาน โดยกำหนดขอบเขต แผนพัฒนา สิ่งส่งมอบ และกำหนดการด้วยตนเอง พร้อมติดตามความคืบหน้าและจัดการ Requirement Changes อย่างเป็นระบบ ไม่ใช่ดำเนินงานเฉพาะตามข้อแก้ไขรายสัปดาห์

สำหรับการสิ้นสุดรายวิชา Seminar ทีมต้องส่ง Final Paper ภาษาอังกฤษในรูปแบบ IEEE ความยาวไม่เกิน 6 หน้า ภายในวันพุธที่ 18 พฤศจิกายน 2569 และตรวจสอบรายละเอียดการส่งใน Google Classroom อีกครั้ง รวมถึงเตรียม Final Presentation ที่แสดงความเข้าใจปัญหา Requirements การออกแบบระบบ วิธีพัฒนา ความคืบหน้า และแผนดำเนินงานต่อใน Senior Project 1 และ Senior Project 2 จนถึงการทดสอบกับผู้ใช้จริงและปรับปรุงระบบ

ทีมต้องใช้ Private GitHub Repository เป็นพื้นที่กลางในการจัดเก็บ Source Code เอกสารฉบับปัจจุบัน แผนงาน และประวัติการเปลี่ยนแปลง โดยให้สมาชิกมีส่วนร่วมผ่าน Commit ของตนเอง และส่งลิงก์ให้อาจารย์เข้าถึง สำหรับการสกัดข้อมูล RS-1 ให้ศึกษาต่อยอดโดยคำนึงถึงความสะดวกของนักวิจัยเป็นหลัก

ประเด็นด้าน Requirements, Workflow, สิทธิ์ผู้ใช้ และสถานะโครงการที่ยังไม่มีคำยืนยันในบทสนทนาครั้งนี้ ให้คงไว้เพื่อสอบถามและตรวจสอบกับ Stakeholder ต่อไป
