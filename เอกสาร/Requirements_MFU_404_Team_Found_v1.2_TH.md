# ข้อกำหนดความต้องการระบบ (Requirements Specification)
## ระบบบริหารจัดการทุนวิจัยส่วนตัว มหาวิทยาลัยแม่ฟ้าหลวง

**ทีม:** 404 Team Found  
**ชื่อโครงการ:** Personal Research Grant Management System for Mae Fah Luang University  
**เวอร์ชัน:** 1.5 — Gap Review Integration (12 พฤศจิกายน 2569)  
**วันที่ปรับปรุง:** 12 พฤศจิกายน 2569  
**สถานะ:** ฉบับร่างเพื่อให้อาจารย์และ Stakeholder ตรวจทาน; ไม่ถือว่าได้รับอนุมัติทุกข้อ  
**เอกสารที่รวม:** Requirements v1.1 (14 ต.ค. 2569) + Requirement Analysis v1.0 (11 พ.ย. 2569) + State Transition Specification + ข้อมูลยืนยันเรื่องอัปโหลดและสกัด RS-1 ล่าสุด + หมายเหตุลายเซ็นจากแบบฟอร์ม RS-1 หน้า 6

> **ขอบเขตการยืนยัน:** Stakeholder ยอมรับแนวทาง **อัปโหลดเอกสาร RS-1 แล้วสกัดข้อมูลเพื่อนำเข้าระบบ** แล้ว แต่ชนิดไฟล์ที่รองรับจริง ฟิลด์ที่สกัดได้ เกณฑ์ความแม่นยำ และวิธีรับมือเอกสารจัดรูปแบบผิดยังต้องกำหนด Acceptance Criteria เพิ่มเติม แบบฟอร์ม RS-1 กำหนดให้ลงนามครบก่อนส่งมายังส่วนบริหารงานวิจัย และหากใช้ลายเซ็นอิเล็กทรอนิกส์ต้องได้รับความยินยอมจากเจ้าของลายเซ็น; วิธีตรวจรับ/ยืนยันผ่าน Web เป็นข้อเสนอการออกแบบของทีม การกล่าวถึงฟังก์ชันอื่นในเอกสารนี้ไม่ได้หมายความว่า Stakeholder อนุมัติทั้งหมด

## 1. วัตถุประสงค์

1. รวมข้อกำหนดเดิมและขยายรายละเอียดสำหรับ Workflow ใหม่ที่ทีมกำลังออกแบบ เพื่อให้นำไปเขียน SRS, Use Case, User Flow, API, Database และ Test Case ได้
2. ครอบคลุมการดำเนินงานของผู้ใช้ Web สามบทบาท ได้แก่ นักวิจัย เจ้าหน้าที่ส่วนบริหารงานวิจัย และผู้ทรงคุณวุฒิ
3. แยกสิ่งที่เกิด **ภายใน Web** ออกจากงานเอกสารทางการผ่าน **e-Office** และการพิจารณาของต้นสังกัดหรือคณะกรรมการ
4. ผูกข้อกำหนดเข้ากับสถานะหลัก 8 สถานะและ Transition Rules (`TR-01`–`TR-16`)
5. ทำให้แต่ละ Requirement ตรวจรับได้ โดยระบุพฤติกรรม ข้อมูล และผลลัพธ์ขั้นต่ำอย่างเป็นรูปธรรม

### 1.1 เอกสารอ้างอิงและลำดับการใช้

- **กฎ / หลักเกณฑ์:** แนวปฏิบัติการทำวิจัยประเภททุนวิจัยส่วนตัว พ.ศ. 2569 ตามที่ Stakeholder ชี้แจง
- **กระบวนการทำงาน:** ขั้นตอนการปฏิบัติการทำวิจัยประเภททุนวิจัยส่วนตัว พ.ศ. 2570 ที่ Stakeholder ส่งให้
- **แบบฟอร์มข้อมูล:** RS-1 ภาษาไทย และ RS-1 Personal Budget ภาษาอังกฤษ
- **การออกแบบสถานะ:** `state-transition.md` ของทีม
- **ฐานวิเคราะห์เพิ่มเติม:** `MFU_Requirement_Analysis_v1.md` และคำแนะนำอาจารย์การประชุมวันที่ 5 พ.ย. 2569

กรณีกฎจากเอกสารสองฉบับไม่ตรงกัน ต้องบันทึกข้อขัดแย้งและถาม Stakeholder; ไม่ให้ทีมตัดสินแทน

### 1.2 ป้ายสถานะข้อกำหนด

| ป้าย | ความหมาย |
|---|---|
| `PROCESS` | มีขั้นตอนรองรับจากเอกสารปฏิบัติปี 2570 หรือข้อมูลกระบวนการที่ทีมได้มา แต่รายละเอียด UI ยังอาจเป็นการออกแบบ |
| `CONFIRMED` | มีคำยืนยันเฉพาะประเด็นจาก Stakeholder เช่น แนวทางอัปโหลด–สกัดข้อมูล |
| `DESIGN` | แนวทางที่ทีมเสนอเพื่อให้ระบบทำงานได้ครบ ต้องนำไปตรวจทาน |
| `OPEN` | ยังไม่อาจระบุพฤติกรรมหรือกฎตายตัว ต้องสอบถาม |

> **หมายเหตุด้านการกำหนดขอบเขต:** v1.1 จำกัดอยู่ที่ Prototype สองบทบาทและ RS-1 บางส่วน ส่วนฉบับนี้ใช้ **ระบบเป้าหมายที่ขยายตาม Workflow** เพื่อให้อาจารย์ตรวจรายละเอียด การจะนำทุกข้อไปลงมือพัฒนาใน Seminar ต้องอนุมัติ Scope และจัดลำดับเป็น MVP เพิ่มเติม

## 2. บทบาทผู้ใช้และขอบเขตความรับผิดชอบ

| Role ID | บทบาท | สิ่งที่ทำใน Web | สิ่งที่ไม่ทำใน Web |
|---|---|---|---|
| `ROLE-01` | นักวิจัย (Researcher) | จัดทำ/นำเข้า RS-1, ยืนยันส่งข้อเสนอ, แนบหลักฐาน, ติดตามสถานะ, ส่งเอกสารปิด | ตัดสินความเห็นชอบของต้นสังกัด, ทำหนังสือทาง e-Office ผ่าน Web โดยตรง |
| `ROLE-02` | เจ้าหน้าที่ส่วนบริหารงานวิจัย (Research Administration Staff) | ตรวจข้อเสนอและเอกสาร, ส่งกลับแก้ไข, บันทึกรับรอง, ดูประวัติ, ตรวจและปิดโครงการ, ประสานการประเมิน | อนุมัติแทนต้นสังกัดหรือคณะกรรมการ, เชื่อมต่อ e-Office อัตโนมัติ |

### 2.1 หลักการกำหนดสิทธิ์

- นักวิจัยเข้าถึงเฉพาะโครงการของตน; เจ้าหน้าที่เข้าถึงเฉพาะระเบียนที่ได้รับอนุญาต; ผู้ทรงฯ เข้าถึงเฉพาะงานประเมินที่มอบหมาย
- การปฏิเสธสิทธิ์ต้องตรวจใน Backend ไม่ใช่ซ่อนปุ่ม UI อย่างเดียว
- สิทธิ์การแก้ไขภายหลังส่งข้อเสนอและสิทธิ์ระดับเจ้าหน้าที่รายบุคคลยังต้องยืนยัน (`OPEN`)

## 3. Functional Requirements (FR) และ Acceptance Criteria (AC)

**รูปแบบ:** `ID | ความต้องการ | เงื่อนไขตรวจรับขั้นต่ำ (AC) | สถานะ`  
**หลักการ:** AC คือพฤติกรรมที่ตรวจสอบได้; ส่วนเงื่อนไขที่ทีมยังไม่ทราบให้ติด `OPEN` ไม่กำหนดเองโดยพลการ

### 3.1 การเข้าถึงและจัดการโครงการ (Common)

| `FR-COM-02` | ระบบต้องตรวจสิทธิ์สำหรับการอ่าน แก้ไข ดาวน์โหลด และเปลี่ยนสถานะ | การเรียก URL/API ด้วย ID โครงการที่ไม่มีสิทธิ์ต้องถูกปฏิเสธ แม้ผู้ใช้เปลี่ยน URL เอง | DESIGN |

| `FR-COM-04` | ระบบต้องแสดงรายละเอียดโครงการที่จำเป็นต่อแต่ละบทบาท | เมื่อเปิดโครงการที่มีสิทธิ์ ระบบแสดงข้อมูลสำคัญและสถานะปัจจุบันสอดคล้องกับฐานข้อมูล | DESIGN |

### 3.2 จัดทำ RS-1 และจัดการร่าง (Researcher)

| FR ID | ความต้องการของระบบ | Acceptance Criteria ขั้นต่ำ | สถานะ |
|---|---|---|---|
| `FR-RES-01` | นักวิจัยต้องสร้างโครงการใหม่ได้ | เมื่อบันทึกโครงการใหม่ ระบบสร้างระเบียนของเจ้าของและตั้งสถานะ `DRAFT` (`TR-01`) | PROCESS/DESIGN |
| `FR-RES-02` | นักวิจัยต้องกรอกข้อมูล RS-1 ตามชุดฟิลด์ที่ระบบรองรับ | บันทึกค่าตามชนิดข้อมูล; ตรวจฟิลด์จำเป็น; ฟิลด์ที่รองรับต้องระบุใน Data Dictionary | PROCESS |
| `FR-RES-03` | นักวิจัยต้องแก้ไขและบันทึกร่างซ้ำได้ | หลังบันทึกและเปิดใหม่ ข้อมูลล่าสุดยังอยู่; สถานะยังเป็น `DRAFT` (`TR-02`) | PROCESS |
| `FR-RES-04` | ระบบต้องรองรับการอัปโหลดไฟล์ RS-1 เพื่อนำเข้าข้อมูล | ผู้ใช้เลือกไฟล์ที่รองรับแล้วระบบรับไฟล์; ไฟล์ไม่รองรับ/เสียหายต้องแสดงสาเหตุโดยไม่สร้างข้อมูลผิดพลาด | CONFIRMED; รูปแบบไฟล์ OPEN |
| `FR-RES-05` | ระบบต้องสกัดข้อมูลสำคัญจากเอกสาร RS-1 ที่อัปโหลด | แสดงรายการฟิลด์ที่สกัดได้และฟิลด์ที่ไม่พบอย่างแยกแยะ; ไม่เติมค่าที่ไม่ทราบเอง; ต้องกำหนด Mapping ต่อฟอร์ม | CONFIRMED; Mapping OPEN |
| `FR-RES-06` | นักวิจัยต้องตรวจสอบและแก้ค่าที่สกัดได้ก่อนยืนยัน | หน้าตรวจข้อมูลแสดงค่าที่สกัด; ผู้ใช้แก้หรือเว้นว่างได้; ระบบไม่ยืนยันเป็นข้อมูลสุดท้ายอัตโนมัติ | DESIGN รองรับ CONFIRMED |
| `FR-RES-07` | ระบบต้องบันทึกข้อมูลที่ผู้ใช้ยืนยันหลังการสกัดลงในร่าง | ค่าที่ผู้ใช้ยืนยันถูกบันทึกในโครงการของตน และกลับมาเปิดตรวจได้ | DESIGN |
| `FR-RES-08` | ระบบต้องเก็บข้อมูลอ้างอิงไฟล์ต้นทางสำหรับการตรวจสอบ | เจ้าหน้าที่ตรวจได้ว่าข้อมูล/ไฟล์ฉบับใดเป็นแหล่งนำเข้า โดยไม่เปิดเผยไฟล์เกินสิทธิ์ | DESIGN |
| `FR-RES-09` | ระบบต้องตรวจความครบถ้วนของข้อมูลก่อนจัดทำฉบับพร้อมยื่น | หากขาดฟิลด์จำเป็น ระบบแสดงรายการที่ต้องแก้และไม่อนุญาตให้ยืนยันฉบับพร้อมยื่น; รายการฟิลด์ต้องกำหนด | DESIGN; Field list OPEN |
| `FR-RES-10` | ระบบต้องแสดงตัวอย่างหรือสร้าง PDF ข้อเสนอได้ | Preview ดาวน์โหลด/ดูได้โดยไม่เปลี่ยนสถานะ; PDF ที่สร้างจากข้อมูล Structured ต้องตรงกับค่าที่บันทึก | PROCESS/DESIGN |
| `FR-RES-11` | ระบบต้องรองรับเอกสาร PDF ฉบับพร้อมยื่นต้นสังกัด | ผู้ใช้ยืนยันฉบับพร้อมยื่น แล้วระบบจัดเก็บเวอร์ชันและเปลี่ยน `DRAFT` → `AFFILIATION_REVIEW` (`TR-03`); วิธีจัดการไฟล์ DOCX ต้นฉบับต้องกำหนด | DESIGN; Trigger OPEN |
| `FR-RES-12` | นักวิจัยต้องปรับข้อเสนอตามความเห็นของต้นสังกัดได้ | บันทึกฉบับแก้ไข/เวอร์ชันใหม่โดยไม่ถือว่าส่งเข้าตรวจเจ้าหน้าที่อัตโนมัติ (`TR-04`) | PROCESS/DESIGN |

**หมายเหตุ RS-1 Import:** การ **สกัดข้อมูลเพื่อเติมฟอร์ม** และการ **แปลงไฟล์ต้นฉบับเป็น PDF** เป็นคนละความสามารถ ห้ามสมมติว่าการสกัดแล้วนำข้อความไปจัดฟอร์มใหม่จะคงรูปแบบเอกสารต้นฉบับทั้งหมด และไม่กำหนด OCR หรือรองรับ PDF สแกนเป็นข้อบังคับจนกว่าจะตกลงรูปแบบไฟล์

### 3.3.1 การจัดการเอกสาร RS-1 ที่ลงนามแล้วและความยินยอม (Researcher)

> **ข้อกำหนดจากเอกสารต้นทาง:** แบบฟอร์ม RS-1 หน้า 6 ระบุว่า “ต้องเซ็นให้ครบก่อนส่งมายังส่วนบริหารงานวิจัย หากใช้ลายเซ็นอิเล็กทรอนิกส์ จะต้องได้รับความยินยอมจากเจ้าของลายเซ็น” โดยมีช่องลงนามสำหรับ **หัวหน้าโครงการวิจัย**, **ที่ปรึกษา (ถ้ามี)** และ **ผู้ร่วมโครงการวิจัย (ถ้ามี)** ข้อความนี้ **ไม่ได้บังคับให้บุคคลเหล่านั้นลงนามผ่าน Web โดยตรง** และไม่ได้กำหนดให้ Web ตรวจสอบตัวตนเจ้าของลายเซ็นได้เอง

| `FR-SIG-02` | นักวิจัยต้องแนบเอกสาร RS-1 ฉบับลงนามแล้วก่อนยืนยันส่งข้อเสนอไปยังเจ้าหน้าที่ | ผู้ใช้ที่มีสิทธิ์อัปโหลด เปิดดู และเปลี่ยนไฟล์ฉบับลงนามก่อนกดส่งได้; หากไม่มีไฟล์ที่กำหนด ระบบไม่ยอมรับการยืนยันส่ง | PROCESS/DESIGN; ประเภทไฟล์ OPEN |

**ขอบเขตสำคัญ:** การติ๊กยืนยันเป็นเพียงคำรับรองของผู้ใช้ **ไม่ใช่หลักฐานยืนยันโดยอัตโนมัติว่าเจ้าของลายเซ็นยินยอมจริง** ระบบไม่ควรเก็บภาพลายเซ็นของผู้อื่นไว้ใช้ซ้ำโดยพลการ และไม่ได้เพิ่มระบบอนุมัติต้นสังกัดหรือ Digital Signature/PKI โดยอัตโนมัติ

**ความเชื่อมโยงกับการส่งข้อเสนอ:** `FR-SIG-02`–`05` เป็นเงื่อนไขตรวจสอบก่อน `TR-05` (`AFFILIATION_REVIEW` → `STAFF_REVIEW`); การแนบไฟล์อย่างเดียว **ไม่** เปลี่ยนสถานะ ตาม `FR-RES-14`

### 3.9 ข้อกำหนดเพิ่มเติมจากการตรวจช่องว่างเอกสาร (Research Standards, Deadlines, Registry)

> **ที่มา:** รายการ 5 ประเด็นที่เพื่อนร่วมทีมตรวจเทียบแนวปฏิบัติและไฟล์ Excel ทะเบียน (12 พ.ย. 2569) ยังไม่ใช่คำยืนยันเฉพาะจาก Stakeholder ว่า Web ต้องทำทุกข้อโดยอัตโนมัติ จึงแยกการบันทึกข้อมูลออกจากกฎบังคับและสิทธิ์ดำเนินการ

| FR ID | ความต้องการของระบบ | Acceptance Criteria ขั้นต่ำ | สถานะ |
|---|---|---|---|
| `FR-STD-01` | ระบบต้องเก็บข้อมูลประเภทมาตรฐานการวิจัยที่เกี่ยวข้องกับโครงการและสถานะการรับรอง | ผู้ใช้ที่ได้รับสิทธิ์สามารถระบุประเภท เช่น จริยธรรมมนุษย์/สัตว์ทดลอง/ความปลอดภัยทางชีวภาพตามกรณี; แสดงว่าไม่เกี่ยวข้อง อยู่ระหว่างดำเนินการ หรือได้รับการรับรองโดยไม่สรุปสถานะเอง | อ้างอิงแนวปฏิบัติ; รายการ/ผู้บันทึก OPEN |
| `FR-STD-02` | ระบบต้องรองรับการแนบหลักฐานการรับรองมาตรฐานการวิจัยที่เกี่ยวข้อง | บันทึกไฟล์ หน่วยงาน/เลขที่รับรอง (ถ้ามี) วันรับรอง และผู้แนบได้; ผู้มีสิทธิ์เปิดตรวจหลักฐานได้ | อ้างอิงแนวปฏิบัติ; ฟิลด์บังคับ OPEN |
| `FR-STD-03` | ระบบต้องแสดงคำเตือนหรือป้องกันการเปลี่ยนไปดำเนินการวิจัยเมื่อโครงการต้องมีการรับรองแต่ยังไม่มีหลักฐาน ตามกฎที่ยืนยันแล้ว | กรณีต้องรับรอง ระบบแสดงรายการสิ่งที่ขาด; การตั้งค่าเป็นเพียงเตือนหรือบล็อก `TR-09` ต้องได้คำยืนยันก่อนเปิดใช้ | OPEN — ห้ามบล็อกอัตโนมัติจากข้อสันนิษฐาน |

## 5. ขอบเขตระบบ (Scope In / Scope Out)

### 5.1 Scope In — ขอบเขตระบบเป้าหมายสำหรับการวิเคราะห์และออกแบบ

1. วิเคราะห์ As-Is/To-Be Workflow และเอกสารจาก Stakeholder; จัดทำ FR/NFR, AC, User Flow, Use Case, State Diagram และฐานข้อมูล
2. บทบาทนักวิจัย: สร้าง/แก้ไข RS-1, อัปโหลด–สกัด–ตรวจแก้ข้อมูล, จัดทำ PDF, แนบหลักฐาน, ยืนยันส่ง, ติดตามสถานะ
3. บทบาทเจ้าหน้าที่: ตรวจข้อมูลและเอกสาร, ส่งกลับแก้ไข, บันทึกผลตรวจผ่าน/รับรอง, จัดการทะเบียนและประวัติ, บันทึกข้อมูลเปลี่ยนแปลง/ขยายเวลา
4. บทบาทผู้ทรงฯ: ดูร่างรายงานที่มอบหมายและส่งผลประเมินผ่าน Web
5. การรับเอกสารขอปิดโครงการทั้งทางรายงาน 5 บทและผลงานเผยแพร่ และการบันทึกปิดโดยเจ้าหน้าที่
6. การตรวจสิทธิ์ การเก็บประวัติสถานะ และการทดสอบระบบ
7. การบันทึกประเภทมาตรฐานการวิจัย/หลักฐานที่เกี่ยวข้อง และข้อมูลทะเบียนตามกรณีที่ Stakeholder รับรองเป็นขอบเขต Web

### 5.2 Scope Out — สิ่งที่ไม่อยู่ใน Web ตามแนวทางปัจจุบัน

1. การอนุมัติข้อเสนอโดยต้นสังกัดภายใน Web
2. การให้คณะกรรมการประชุม ลงมติ หรืออนุมัติใน Web (ขั้นตอนเป็น **เพื่อทราบ**)
3. การเชื่อมต่อ e-Office ผ่าน API หรือการแทนที่หนังสือราชการทางการทั้งหมด
4. การใช้งานจริงทั้งมหาวิทยาลัย การรับประกัน Production Scale และการดูแลระบบระยะยาวในช่วง Seminar
5. ระบบร่างหนังสือราชการครบชุดหรือบริการอื่นนอกเหนือจากทุนวิจัยส่วนตัว
6. ฟังก์ชันประเมินรายงานหลายรอบโดยอัตโนมัติ โดยยังไม่มีเกณฑ์ยืนยัน
7. ระบบให้ผู้เกี่ยวข้องลงนามดิจิทัลแบบ PKI ภายใน Web หรือการอนุมัติต้นสังกัดผ่าน Web (ยังไม่มีข้อกำหนดให้ทำเช่นนั้น)
